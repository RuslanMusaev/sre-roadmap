Evidence и вывод

В короткий день: 5 + 20 + 5 минут. В длинный: 10 + 40 + 10. Сессии не привязаны к датам: дежурство или реальный инцидент могут сдвинуть план. Незавершённую задачу продолжай в следующую сессию.

Отмечай задачу после проверки результата. Все поломки воспроизводи в отдельной лаборатории на синтетических данных. Базовый стенд: Linux VM, Git, контейнерный runtime; Kubernetes появится на неделе 3. Запускай тяжёлые компоненты по очереди. Ориентир для компактного стенда — 4 vCPU / 8 GB RAM; совместный stack может потребовать больше.

План по неделям

01 → 12
Итоговый pet-project

Incident-ready service

Небольшой API принимает событие, сохраняет данные в PostgreSQL и публикует его в Kafka. Worker обрабатывает событие идемпотентно. Kubernetes и Helm описывают запуск, Argo CD доставляет изменения из Git.

Client → API → PostgreSQLAPI → Kafka → WorkerMetrics → Prometheus → GrafanaTraces → OTel → Tempo / JaegerGit → CI → Argo CD → Kubernetes

Критерии готовности

  • README позволяет повторить запуск и smoke test без догадок; версии и ограничения записаны.
  • Проверены probes, requests/limits, RBAC, NetworkPolicy и сохранность данных на PVC.
  • Есть RED dashboard, SLI/SLO, рабочий alert, trace и связь с логами.
  • Три инцидента подтверждены evidence; после исправления проверены latency, ошибки, lag и обработка событий.
  • Есть rollback через Git, CLI диагностики, runbooks и три кратких postmortem.

Собирай lab постепенно с недели 1. Неделя 12 — интеграция и проверка готовых частей. Thanos и отказоустойчивый Kafka cluster — расширения после основного проекта; для ограниченного стенда достаточно схемы Thanos и явно отмеченного разбора replication.
